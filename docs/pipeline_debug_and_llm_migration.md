
## Pipeline Debugging Report and Migration from Qwen 2.5 to Gemini 2.5 Flash

---

# 1. Overview

This document summarizes:

1. The rationale for migrating Agent 2 from Qwen 2.5 to Gemini 2.5 Flash.
2. Major bugs discovered during integration of the multi-agent surveillance optimization pipeline.
3. Fixes applied to stabilize iterative optimization.
4. Remaining known limitations.

---

# 2. Why Agent 2 Was Migrated From Qwen 2.5 To Gemini 2.5 Flash

Agent 2 is responsible for strategy generation based on route analysis produced by Terrain Intelligence (Agent 1).

Its responsibilities include:

* Corridor prioritization
* Route vs coverage weighting
* Bottleneck analysis
* Generation of strategy JSON for downstream camera placement

Initially, Agent 2 used a locally hosted Qwen 2.5 3B Instruct model.

During testing, several issues were encountered.

## Problems with Qwen 2.5

### 1. Inconsistent JSON Output

Although prompts explicitly requested JSON-only responses, Qwen frequently generated:

* Extra explanatory text
* Template placeholders
* Missing fields
* Invalid JSON formatting

Example:

```json
{
  "strategy_decision": "route_elimination or coverage_expansion - REQUIRED"
}
```

instead of actual values.

This caused parsing failures and forced the pipeline to use fallback defaults.

---

### 2. Complex Post-Processing

Additional logic was required for:

* JSON extraction
* Response cleaning
* Validation
* Missing-field repair

This increased maintenance complexity.

---

### 3. Hardware Dependency

Qwen required:

* GPU access
* HuggingFace authentication
* Local model downloads
* VRAM management

making deployment more complicated.

---

### 4. Slower Development Cycle

Every model update required:

* Re-downloading weights
* Re-testing prompts
* Local debugging

which slowed experimentation.

---

### 5. Agent 2 Requirements Were Relatively Small

Agent 2 only generates:

```json
{
  "route_weights": 0.7,
  "coverage_weights": 0.3,
  "priority_corridor": "center"
}
```

This does not require heavy local inference.

---

## Benefits of Gemini 2.5 Flash

Gemini 2.5 Flash provides:

### Reliable Structured Output

Better adherence to JSON instructions.

### API-Based Deployment

No local model hosting.

### Faster Iteration

No model downloads.

### Reduced Infrastructure Complexity

No GPU requirement.

### Better Maintainability

Simpler integration and debugging.

## 3. Pipeline Bugs Identified During Integration

---

## Bug 1: Agent 2 Strategy Was Not Adapting Across Iterations

## Problem

Despite significant route reductions between iterations, Agent 2 repeatedly generated:

```json
{
  "route_weights": 0.7,
  "coverage_weights": 0.3
}
```

for every iteration.

The strategy remained unchanged even when corridor statistics changed substantially.

---

## Root Cause

Fallback repair logic was overwriting LLM outputs.

The pipeline often replaced generated values with defaults.

---

## Fix Applied

* Added strict validation
* Improved JSON extraction
* Prevented default values from replacing valid outputs
* Migrated to Gemini for more reliable structured responses

---

# Bug 2: Camera Scoring and Visibility Evaluation Were Inconsistent

## Problem

Agent 3 ranked camera candidates using:

* Bottleneck frequency
* Distance-to-center metrics

However, Visibility Evaluator selected cameras using:

* Actual route interception
* Coverage gain

This produced different rankings.

---

## Root Cause

Camera scoring used proxy metrics while visibility evaluation used real environmental metrics.

---

## Fix Applied

Camera Scoring was repositioned as a lightweight pre-filtering stage.

Final camera selection remains controlled by Visibility Evaluation.

---

# Bug 3: Iterative Route Optimization Loop Was Broken

## Problem

Iteration 0:

```text
360 routes
↓
124 routes remaining
```

Iteration 1 unexpectedly reverted to:

```text
360 routes
```

instead of continuing from:

```text
124 routes
```

---

## Root Cause

Environment Update continuously loaded:

```text
paths_1.json
```

instead of:

```text
paths_iter_N.json
```

generated by previous iterations.

---

## Fix Applied

Environment Update now:

* Produces `paths_iter_N.json`
* Returns next route file
* Allows Iteration Manager to pass the correct route set forward

This restored proper iterative optimization.

---

# Bug 4: LLM-Generated Bottlenecks Were Hallucinated

## Problem

Agent 2 occasionally generated bottleneck coordinates that never appeared in Terrain Intelligence outputs.

Example:

```text
1_1
4_3
```

even though those locations were not present in route statistics.

---

## Root Cause

Agent 2 was allowed to invent bottleneck locations.

---

## Fix Applied

Agent 2 now consumes bottlenecks produced by Terrain Intelligence.

The LLM no longer generates bottleneck coordinates.

Instead it only:

* Prioritizes
* Weights
* Explains

using validated bottleneck data.

---

# Bug 5: Coverage Metric Is Not Physically Meaningful

## Problem

Coverage scoring currently uses:

```python
coverage_score = 1 / (1 + distance_to_center)
```

This assumes:

```text
Closer to map center
=
Better coverage
```

which is not physically accurate.

Real coverage depends on:

* Terrain geometry
* Elevation
* Occlusions
* Visibility
* Camera orientation
* Range
* Field of View

---

## Current Status

This issue remains unresolved.

The metric is currently used only as a lightweight heuristic.

Future versions should replace it with:

* Visibility area estimation
  or
* Raycast-based coverage computation

derived from actual terrain visibility.

# 4. Additional Pipeline Improvements

The following infrastructure changes were also implemented:

### Iteration-Based Outputs

Instead of overwriting files:

```text
strategy.json
summary.json
```

the pipeline now stores:

```text
summary_iter_0.json
summary_iter_1.json
summary_iter_2.json

strategy_iter_0.json
strategy_iter_1.json
strategy_iter_2.json
```

allowing:

* Reproducibility
* Debugging
* Historical analysis

---

### Runtime State Tracking

Environment Update now maintains:

```text
paths_iter_1.json
paths_iter_2.json
paths_iter_3.json
```

which preserves optimization progress across iterations.

# 5. Current Pipeline Status

Current architecture:

Terrain Intelligence
↓
Agent 2 (Gemini 2.5 Flash)
↓
Candidate Selector
↓
Camera Scoring
↓
Visibility Evaluator
↓
Environment Update
↓
Iteration Manager

The optimization loop now correctly propagates:

* Updated routes
* Updated summaries
* Updated strategies
* Updated visibility decisions

between iterations.

The only major known limitation remaining is the coverage metric approximation discussed in Bug 5.
